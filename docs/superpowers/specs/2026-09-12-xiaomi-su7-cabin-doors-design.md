# Xiaomi SU7 四门与真实座舱体验增量设计

**日期：** 2026-09-12  
**项目：** `xiaomi-su7-interactive`  
**设计基准：** 用户提供的 Xiaomi SU7 三维交互参考站  
**方案：** 参考逻辑复刻 + 质量强化

## 1. 背景与目标

现有版本已经具备外观/座舱模式、前排车门联动、内饰换色以及主驾/副驾/后排镜头切换，但存在三项明显不足：

1. 只识别并控制前排两扇门，没有覆盖模型中的 `DOOR1–DOOR4`。
2. 座舱镜头仍偏向外部观察，未形成参考站所展示的真实车内空间感。
3. 座舱屏幕、方向盘、仪表台、中央通道和座椅缺乏独立灯光与材质层次。

本轮目标是在保留当前页面结构、视觉语言和 GitHub Pages 发布方式的前提下，补齐四门一键全开/全关、正确门轴动画、真实三座席视角和座舱细节强化。交互逻辑以参考站为基准，但修正其可见的门体错位、穿模、过曝和材质发灰问题。

## 2. 范围

### 2.1 本轮包含

- 识别并控制四扇车门。
- 一键全开/全关。
- 进入座舱时自动全开四门。
- 在座舱内关门后保持当前座舱模式和座席镜头。
- 主驾、副驾、后排三个真实车内机位。
- 座舱灯光、屏幕自发光和内饰材质强化。
- 三个座席对应的说明卡与细节标签。
- 能力降级、自动化测试、视觉回归和 GitHub Pages 验证。

### 2.2 本轮不包含

- 单独控制某一扇车门。
- 后备箱、前备箱或车窗动画。
- 方向盘、座椅、屏幕的二级可操作功能。
- 替换现有 GLB 模型或增加新的大型外部资源。
- 与本轮座舱体验无关的页面结构重做。

## 3. 交互设计

### 3.1 进入座舱

点击“座舱”标签或“进入座舱”按钮时：

1. 模式切换为 `cabin`。
2. 四扇车门自动执行全开动画。
3. 相机从当前外部机位平滑过渡至默认主驾机位。
4. 控制器展示内饰配色、主驾/副驾/后排和车门按钮。
5. 车门按钮文案变为“关门”。
6. 右下角说明卡切换为主驾座舱内容。

### 3.2 一键开关四门

- 四门由同一按钮统一控制，不新增单门操作。
- 点击“关门”时，四门同时平滑关闭；座舱模式、座席选择和相机位置保持不变。
- 点击“开门”时，四门同时平滑打开；镜头不重置。
- 切换主驾、副驾、后排只改变镜头与说明内容，不重复触发车门动画。
- 返回外观模式时恢复外部相机，但车门保持用户最后选择的状态，不自动打开或关闭。
- 动画进行中再次点击时，从当前角度平滑反向，不产生跳变。

### 3.3 座席切换

- **主驾：** 聚焦方向盘、前挡、仪表台和中控屏。
- **副驾：** 从副驾位置横向观察中控屏、方向盘、中央通道和副驾仪表台。
- **后排：** 从后排中央向前观察双前排座椅、中控屏和中央扶手。

每个座席均更新右下角说明卡的标题、描述和三个细节标签。切换过程中使用短距离、低眩晕的相机缓动。

## 4. 车辆模型与门轴设计

### 4.1 四门映射

模型加载阶段识别 `DOOR1–DOOR4`，输出明确的四门结构：

- 左前门
- 右前门
- 左后门
- 右后门

能力对象分别记录四门是否可用，避免使用“左右各一扇”的旧结构。

### 4.2 门轴

- 每扇门创建独立铰链节点。
- 铰链基点位于门体靠近 A 柱或 B 柱的真实转轴位置，而不是使用门模型中心点。
- 通过保持世界变换的方式把门体挂载到铰链，避免模型瞬移。
- 左右门旋转方向相反；前后门分别校准最大角度，防止与翼子板、B 柱或后轮拱穿插。
- 动画采用 ease-in-out 缓动，并保留当前角度作为下一次动画起点。
- 车身根节点、座椅、内饰和车窗不得随门轴旋转。

## 5. 座舱相机设计

### 5.1 主驾机位

- 相机位于驾驶员头部高度。
- 方向盘位于画面中下部，前挡、中控屏和仪表台同时可见。
- 采用较窄 FOV，减少车内近距离透视变形。

### 5.2 副驾机位

- 相机位于副驾座位头部位置。
- 视线横向指向中控屏和驾驶区域。
- 保留中央扶手、杯架与副驾仪表台作为空间参照。

### 5.3 后排机位

- 相机位于后排中央略高位置。
- 两张前排座椅形成近景框架。
- 视线指向中控屏、方向盘和中央通道，突出前后排空间关系。

### 5.4 近距离渲染

- 为座舱视角单独校准 near clipping plane，避免座椅、车顶和车门突然消失。
- 相机不得穿过车身、座椅或挡风玻璃实体。
- 切换座席时只插值相机位置、目标点和 FOV，不改变车辆根节点姿态。

## 6. 座舱灯光与材质

### 6.1 屏幕

- 单独识别中控屏与仪表屏材质。
- 使用受控的冷色自发光，保证屏幕亮而不泛白。
- 屏幕亮度不依赖整体环境曝光。

### 6.2 内饰层次

- 仪表台、方向盘、中央通道、座椅和门板分别校准颜色与粗糙度。
- 内饰换色只影响目标内饰材质，不污染玻璃、屏幕、金属件或车身。
- 保留黑色、棕色、红色和灰紫色方案，与现有控制器兼容。

### 6.3 座舱补光

- 增加柔和顶灯，提供整体轮廓。
- 增加低强度脚部氛围光。
- 使用局部冷光模拟中控屏对周围表面的反射。
- 进入座舱时降低外部环境曝光或调整灯光权重，避免车外过曝和内饰发灰。
- 退出座舱时恢复外观模式的灯光与曝光。

## 7. 界面与内容

控制器沿用参考站的结构：

- 外观 / 座舱模式切换。
- 车身色与内饰色。
- 主驾 / 副驾 / 后排。
- 一键开门 / 关门。

座舱说明卡按座席切换：

- **主驾：** 主驾位置、方向盘、前挡视野。
- **副驾：** 副驾位置、侧窗、中控屏。
- **后排：** 后排中央、前排座椅、中央扶手。

按钮需保留键盘操作、焦点样式、`aria-pressed` 与禁用状态。移动端触控区域不得小于 44px。

## 8. 状态与组件边界

- `vehicle-state` 负责模式、内饰、车门统一状态和当前座席。
- `load-vehicle` 负责节点识别、门轴创建、材质分组和能力报告。
- `vehicle-controller` 负责四门动画、内饰颜色和灯光/材质状态应用。
- `camera-controller` 负责三个座舱预设及外观/座舱之间的平滑过渡。
- `bind-controls` 只把界面事件映射到 store action，不直接操作 Three.js 对象。
- UI 说明卡根据 store 状态渲染，不读取 Three.js 内部对象。

该边界保证四门识别、动画、相机和 UI 可分别测试与替换。

## 9. 降级与错误处理

- 只识别到部分车门时，仍控制已识别车门，并在能力状态中准确报告；不让座舱整体失效。
- 完全未识别车门时禁用开关门按钮，但保留座舱视角。
- WebGL 或模型加载失败时展示静态车辆图、座舱说明和禁用控制器。
- 低性能设备限制像素比、阴影和补光数量，但保留四门状态与三个相机机位。
- `prefers-reduced-motion` 开启时缩短或取消车门与镜头缓动，最终状态保持一致。
- 所有动画和事件监听在页面销毁、加载重试或 WebGL context 丢失时正确清理。

## 10. 测试设计

### 10.1 单元测试

- 识别 `DOOR1–DOOR4` 并创建四个独立门轴。
- 验证左右前后门的旋转方向和目标角度。
- 验证动画中反向切换从当前角度继续。
- 验证进入座舱自动开门。
- 验证关门不退出座舱。
- 验证切换座席不重复触发门动画。
- 验证返回外观保持门状态。
- 验证三个座舱相机预设位置、目标和 FOV 不同且位于车舱范围内。
- 验证内饰换色和屏幕自发光只作用于对应材质。

### 10.2 E2E

- 进入座舱后四扇门均产生正确角度变化。
- 一键关门后四扇门回到闭合角度，模式仍为 `cabin`。
- 主驾/副驾/后排切换后，相机诊断数据与说明卡同步更新。
- reduced-motion 下状态立即到位。
- 桌面端生成三个座席视觉回归截图。
- 移动端控制器无遮挡、按钮尺寸合格。

### 10.3 发布验证

依次执行：

1. 单元测试。
2. Production build。
3. Playwright E2E。
4. 确认正式 `dist` 不包含测试诊断入口。
5. GitHub Actions 构建与 Pages 部署。
6. 在线检查页面标题、四门开关与三个座舱视角。

## 11. 验收标准

- 四扇门可一键全开/全关，动画平滑且可中途反向。
- 门体无漂移、无明显穿模、不带动车身或内饰。
- 进入座舱自动开门，关门后仍停留在当前座席。
- 主驾、副驾、后排均为真实车内镜头，并清楚展示对应重点。
- 中控屏与仪表屏可读，内饰有层次，车外环境不过曝。
- 三个座席说明卡内容正确，键盘与移动端操作可用。
- 自动化测试、构建、E2E 和 GitHub Actions 全部通过。
- GitHub Pages 在线版本更新并可正常访问。
